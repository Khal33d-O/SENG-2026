# W1.10 lab: smoke checks and a correlated request

This single 70-minute challenge asks you to execute a smoke-test checklist, locate one request in Grafana and predict
the effect of a small configuration change before verifying it. The supplied page loads the familiar reference board;
its server also offers **Slow** and **Overdue** timing fixtures. You do not implement these routes, the browser timing
behaviour, logging middleware, transport or Grafana view.

## Timing

| Block | Minutes |
|---|---|
| Retrieval, concepts and three worked examples | about 50 |
| Guided practice (checklist rows, join a response to a record, environment change, failed expectation) | about 30 |
| Challenge: Tasks 1–6 | 70 |
| Recap and knowledge check (9 + 6) | 15 |

## Outcomes

* Describe the supplied components and the minimum evidence that the deployment works.
* Explain how a health check, log entry and prepared Grafana view help locate a failure.
* Write and execute smoke checks for the front end, API response and configuration.
* Annotate one request's telemetry and explain the observed effect of a bounded configuration change.

## Files you own and supplied semantics

Edit only your workspace's `client.json`, `runtime.env` and your copy of the verification document
([`evidence.md`](evidence.md)). The application ([`../../projects/code/app/`](../../projects/code/app/), release
`foundation-observe-a`), the helper [`starter/run.py`](starter/run.py), the logging configuration
([`observability/`](observability/)) and the dashboard are read-only teaching equipment.

| Input or observation | Supplied meaning |
|---|---|
| `deadlineMs` | Integer 40–650; complete-body waiting limit for each HTTP attempt |
| `retries` | Integer 0–2; additional attempts after an unavailable result |
| Total configured budget | `deadlineMs × (retries + 1)` must not exceed 650 ms |
| Actual caller allowance | Slow-board receipt must occur within 750 ms, allowing bounded browser overhead |
| Received HTTP error | Ends this supplied action; it is not retried |
| `request_id` | Unique identifier generated by the supplied client for one attempt |
| `action_id` | Identifier shared by attempts belonging to one click |
| `result_status` | Server handler's selected result when that handler supplied one |
| `response_status` | Server response object's status at completion recording |
| `caller_aborted` | Whether the server observed cancellation by that recording point |

The workspace begins with `client.json`:

```json
{"deadlineMs":80,"retries":0}
```

and `runtime.env` containing `LAB_ENV=workshop-blue`.

## Setup and starting checkpoint

The facilitator prepares Python, .NET, Chromium (Python Playwright) and the pinned local Loki/Grafana images; the
helper refuses to download missing images. A ready personal workspace should be provided before teaching. Paths such
as `/tmp/w110-lab` are examples: use your own fresh destination (on Windows, any new folder path).

```bash
python3 starter/run.py prepare /tmp/w110-lab
python3 starter/run.py fixtures
python3 starter/run.py browser /tmp/w110-lab reference --expect received
```

Open the printed application URL manually as well. Select the fixture and click **Load board**. The **Browser
observation** block describes the action and its attempts; **Received body** shows the complete body actually obtained.
The static board picture is a reference illustration, not proof that a new request returned.

**Browser checks.** With Chromium/Playwright prepared, `browser` drives the real page. Without it, the helper uses an
**emulated client** applying the same `client.json` rules and labels every result accordingly; record which you used.

Worked examples: [`../../examples/w1-10/README.md`](../../examples/w1-10/README.md).

## Task 1: write and execute the baseline checklist

Finish expectations for the page, reference API body, public environment and health route before executing them; each
row needs an expected result, actual observation and evidence location. Run the reference case, then:

```bash
python3 starter/run.py browser /tmp/w110-lab missing --expect http-error
python3 starter/run.py browser /tmp/w110-lab slow --expect received
```

The initial Slow receipt check is **expected to fail**. Preserve its output and `last-observation.json` before making
another request. Confirm that the failure is lack of receipt for this fixture, not a failed setup command.

## Task 2: locate and annotate the failed attempt

```bash
python3 starter/run.py query /tmp/w110-lab last-request
python3 starter/run.py grafana /tmp/w110-lab last-request
```

Open the saved Grafana URL and inspect the full row. Match request ID, path and environment; compare caller elapsed time
with server processing time, selected result and cancellation state, and state the interval each clock measures. Do not
describe a server-selected 200 as a received 200 unless the browser observation supports it. If the query is empty,
check workspace, identifier, interval and record delivery before declaring that no request executed.

## Task 3: predict and apply a bounded configuration change

The requested Slow result is complete receipt of the reference board within the caller allowance. Choose allowed
values, write your prediction (browser outcome, attempts, completion fields, environment, preserved reference/health
behaviour) and a plausible competing configuration with the check that distinguishes it. Edit between backup and apply:

```bash
python3 starter/run.py backup /tmp/w110-lab
python3 starter/run.py apply /tmp/w110-lab
```

The helper keeps the compiled DLL unchanged, validates both files, restarts the application and serves the chosen client
values. Reload the page after applying. If you choose green, supply `--environment workshop-green` to the browser helper.

## Task 4: verify the chosen and competing proposals

Run the Slow receipt check and correlate its new request; record the actual elapsed time and complete body. Then test
the competing configuration against the same Slow promise (preserve your chosen values first), explain its outcome,
restore your chosen values and rerun. A validator rejection demonstrates an input limit, not a functional counterexample:
your rejected proposal should be valid under the budget but fail the browser result for an explained reason.

## Task 5: preserve behaviour at the longer boundary

```bash
python3 starter/run.py browser /tmp/w110-lab overdue --expect unavailable
python3 starter/run.py query /tmp/w110-lab last-request
```

Overdue is deliberately slower than the allowed waiting budget, so a bounded unavailable outcome is correct. Compare its
later server record with the browser observation. Then rerun Reference and Missing, checking the intended environment
and health.

## Task 6: package the procedure and individual explanation

Complete the checklist and annotate one correlated request: first failure, prediction, chosen result, competing result
and overdue boundary, with commands and raw evidence paths. Explain individually why a healthy resource alone does not
prove this browser/API interaction works, using your own request.

## Acceptance criteria

- [ ] Page, reference response, public environment and health expectations were written and executed.
- [ ] The initial Slow receipt failure was reproduced from a ready baseline and preserved.
- [ ] An actual Grafana row and raw query match the failed request and its context.
- [ ] The annotation distinguishes server-selected status from caller receipt and identifies cancellation/timing evidence.
- [ ] A prediction preceded the bounded configuration change; Slow now receives the expected complete board within the allowance.
- [ ] A valid competing configuration was tested against the same promise and its causal result explained.
- [ ] Overdue remains bounded and unavailable; Reference and Missing retain their defined behaviour.
- [ ] The procedure includes version, intended environment, commands, evidence paths, recovery and individual assistance.

## Recovery and optional depth

Run backup before restoring a saved file. Both `client.json` and `runtime.env` are required; a missing required file
causes failure before a backup directory is created. Each successful invocation creates a distinct directory under
`saved/`, and `backup-manifest.json` records whether the optional last observation was absent or preserved. Copy the
chosen saved files back, apply them and verify a fresh request. A malformed or over-budget configuration fails before
restarting the active process. For a broken preparation, use a new workspace path and keep the old directory.

After essential acceptance, query a nonexistent identifier and explain the scope of the empty result. When the
facilitator releases your services:

```bash
python3 starter/run.py stop /tmp/w110-lab
```

## Knowledge check (9 minutes)

1. The health endpoint returns 200 and Healthy. A browser opens the page but its reference-board action receives no complete response. Which statement is supported?
   A) The healthy response proves that the browser received the reference board. B) The health route answered; the failed browser interaction still needs its own request evidence. C) An unavailable browser result proves that the health response was fabricated. D) Repeating the health request alone establishes the missing board response.
2. A client caches responses by URL and language with an ETag. The English Reference request sends "board-v6", receives 304 and displays the required cached board; the server record shows 304 and no body transfer. Which conclusion and evidence suffice without claiming a fresh download?
   A) Mark the display unavailable because a zero-byte body means no usable representation. B) Use the newer Preview body. C) Retain the selected Reference entry's URL, language, validator and body with the current 304 record and displayed result; record successful reuse rather than a fresh body transfer. D) Relabel the 304 record as a newly downloaded 200.
3. Browser and server wall clocks have an unmeasured offset; the browser says it sent at 12:00:00.500, the server received at 12:00:00.100; local durations 180 ms and 150 ms; identifiers match. Which timing conclusion is defensible?
   A) The request travelled backward in time. B) Latency is exactly -400 ms. C) Discard both elapsed durations. D) Do not subtract the unmatched wall clocks; retain the local durations and obtain clock-offset or shared-clock evidence.
4. A shared report keeps only the first eight characters of each request ID; two simultaneous requests share that prefix (one succeeded, one cancelled). Which handover preserves a defensible correlation without exporting full IDs?
   A) Use the authorized full-ID join locally, then assign distinct report aliases with an explicit local mapping. B) Join both rows to the successful request. C) Drop the cancelled row. D) Conclude that the server processed one request twice.
5. A logger keeps every error and one in ten successes. A reviewer needs evidence for one known successful request with no stored row; a temporary switch can retain all completion records for this route. What procedure supports the requirement?
   A) Infer the request never reached the server. B) Temporarily enable complete recording for the selected route, run a fresh identified request, verify its row and restore the sampling policy. C) Log all request bodies and credentials. D) Copy a different row and replace its ID.
